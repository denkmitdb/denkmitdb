# Review 2026-11: concept, architecture, use cases, push design and roadmap

Reviewed: `denkmitdb/denkmitdb` main @ 24e53e6 (worktree `daemon`), 2026-11-10. Read-only review by Claude Fable 5.2 (`claude-fable-5-2`); second opinions from Codex CLI 0.166.0 (two `codex exec --sandbox read-only` runs against the repo) and Gemini (two grounded searches, two critique chats).

> A point-in-time review, kept as written. It is input to [ROADMAP.md](../ROADMAP.md), not a
> decision record: line numbers refer to commit 24e53e6, and statements marked as unverified
> (section 7) were not tested.

## Executive summary

- **The mechanism is real and well built; the headline claim is ahead of the evidence.** Verify-before-index, entry-to-database binding, deterministic rules in the manifest and frozen wire fixtures are the strongest part of the project. But "agents that don't trust each other" has only ever been exercised on four machines of one owner.
- **"Don't trust each other" currently covers integrity and attribution, not availability.** An open-membership database has no quotas, no timestamp bound and no head-announcement rate limit: a stranger cannot forge or overwrite, but can fill disks and force full tree rebuilds on every replica.
- **"No server" should become "no operator you have to trust".** Two of the four live nodes can only reach the mesh through one public seed (one of them only through its wss/443 proxy). A seed cannot forge or alter anything, but it can withhold, and it sees all metadata.
- **The honest present-tense user** is one person or a small team running coding agents from different vendors on several machines and networks. The cross-organization user stays hypothetical until owner-level identity (delegation) exists and one real external party has used it.
- **Practical ceiling today: about 10k records comfortable, 100k the upper bound, 5–20 peers, a few concurrent writers.** The index lives in RAM and is rebuilt by re-verifying every entry on open; fresh joins cost 10–14 ms per entry.
- **Eight use cases are specified below; six can be shown today.** The three to lead with: intrusion refused at the tool and at the wire, a signed release gate across machines, and a sealed hand-off across a firewall.
- **Push: build "pull with a doorbell" first.** A change feed in the library, a daemon journal with cursors, an inbox convention, a one-line unread notice on every tool result, and turn-boundary hooks for Claude Code and Codex. True push into an idle session exists only in Claude Code (channels, `asyncRewake` hooks) and should come second, behind a sender allowlist.
- **Three small defects found during review**: `memory_get`/`memory_list` can pair an old value with a new writer; the relay's `tools/list_changed` does nothing in Codex 0.166 (feature flag off); a validity-rejected write still signs and pins a block locally.
- **One design flaw in a planned feature**: issue #31 proposes DHT provider records keyed by the database address. Reads are ungated, so the address is the only read secret; publishing it makes every database enumerable. Use a derived rendezvous key.
- **Roadmap: publish, then one manifest v3 that bundles delegation, value-size/digest policy inputs and succession, rather than three format bumps.** Relays before DHT; own batched sync protocol before any Iroh work; cut "P2P git for agents" from the roadmap.

## 1. Concept and vision critique

### 1.1 Is the positioning sharp and true?

"Signed fact exchange between agents that don't trust each other — peer to peer, no server" is sharp. It is true of the mechanism and not yet true of the evidence.

**True.** Every entry is a JWS bound to its database (`src/database.ts:444`, KNOWN_ISSUES #24). Ingest fetches the entry, verifies the signature, checks the binding and evaluates both manifest rules before the index is touched (`processLeafMerging`, `src/database.ts:859–921`). Unsigned tree nodes are never trusted. Rule evaluation is a pure function of manifest and signed entry (`src/policy.ts:31–43`), so honest replicas agree without talking. This is the part nobody else in the agent-tooling space has.

**Over-claimed or weak.**

1. *"Don't trust each other" is integrity-only.* Under `public` or `namespace-per-writer`, identities are free and nothing limits what a stranger can make every replica store. The 64 KiB cap lives in the MCP tool (`mcp/src/tools.ts:163`), not in the library or the rules. The default validity rule is `true` (`src/database.ts:144–148`) and timestamps are only required to be non-negative safe integers (`src/protocol/entry.ts:71`). Any topic participant can make a replica fetch heads (`src/database.ts:1106`). A hostile party cannot lie in your name; it can degrade your node.
2. *"No server."* `askvivo` (NAT) and `macbook` (HTTPS-only firewall) reach the mesh only through `open`; `macbook` only through Caddy on 443. That is a connectivity single point of failure. The accurate claim: no operator has authority — any always-on peer can be a seed, and a seed can withhold or observe but not forge, alter or reorder.
3. *"Memory."* It sets expectations of retrieval, relevance and decay that the project deliberately refuses (VISION "What we deliberately do not build"). VISION already says memory is the distribution channel, not the product; the README tagline still leads with it.
4. *Identity is a key.* A reader sees eight unrelated CIDs, not one owner with four machines and three agent clients. Names inside identity blocks are self-asserted (`src/identity.ts:29–32`). Until delegation phase 2 there is no "party".
5. *Same-user agents are not isolated.* Choosing a socket selects an identity; any process of the OS user can use any of them (`mcp/src/daemon.ts:69–72`, documented in specs/delegation.md §11). "Claude and Codex each sign as themselves" is a labeling convenience, not a security boundary.
6. *Last-writer-wins on writer-chosen clocks* is a weak base for what agents ask for next: queues, claims, append-only logs. The docs say so; the launch post should keep saying so loudly.

### 1.2 The real user and the wedge

| Alternative | What it does better | What DenkMitDB has that it lacks |
|---|---|---|
| Shared files, git, Syncthing | Simple, diffable, history | Works where there is no shared filesystem or credential (a chat app at home, a laptop behind an HTTPS-only firewall); per-entry signer; write rules enforced by every copy |
| Redis, Postgres | Queries, transactions, CAS, speed | No operator; no open inbound port on most nodes; a compromised node cannot rewrite others' records |
| mem0, Zep, Letta, LangMem | Retrieval, summarization, graphs | Signatures, multi-owner writes, no service account. They are centralized and unsigned (Gemini grounded search) |
| A2A and other agent-messaging protocols | Task lifecycle, discovery, streaming RPC | Shared durable state that outlives both endpoints being online |
| Automerge, Yjs, Electric | Rich merges, mature ecosystems | Authenticated writers and admission rules. Jazz is the closest: signed CoValues with group permissions, but it syncs through servers |
| OrbitDB | Same stack, older | Maintained; verify-before-index; rules bound in the manifest |
| Nostr | Signed events, many relays, large network | Rules replicated with the data and enforced at ingest; a key-value state rather than an event stream |
| Willow + Meadowcap, p2panda, iroh-docs | Stronger designs for capabilities and sync | An agent product today (daemon, MCP, three clients working). These are the architectural peers to watch |

The wedge that holds today: **vendor-neutral, attributable shared state for agents on machines that cannot otherwise reach each other, with no service to run.** The wedge the vision wants — separate organizations — needs three things that do not exist yet: owner identity, a way to change membership without a new database, and resource limits.

Recommended one-sentence positioning:

> Signed, replicated facts for AI agents on different machines and vendors: every entry attributable to a key, every replica enforcing the same write rules, and no operator who can alter them.

Keep `memory_*` as tool names (agents find them); stop leading with "memory" in prose.

### 1.3 What is genuinely unique

The combination, not any single part: per-write signatures, plus rules that travel inside the database and are enforced at every replica's ingest, plus no operator, plus a working agent integration. Two properties deserve more airtime than they get:

- `provenance()` returns the entry CID, a content hash of the signed record. An approval that names an entry CID is bound to exact content (use case 4).
- Policies are total functions with a closed operator set and a version number. That makes a second implementation feasible — which is the only real proof of "any replica can check".

## 2. Architecture review

### 2.1 Strengths

- **Verify, then index**, with pin-before-index (`src/database.ts:888–916`) and a bounded remote tree walk (`TreeWalkBudget`, `src/database.ts:87`, `isPlausibleHead` `:843`).
- **Determinism discipline**: no node-local inputs reach a rule; only literal `true` authorizes (`src/policy.ts:38`).
- **Small frozen surface**: `src/index.ts` exports the whole API; `test/wire` pins bytes and CIDs.
- **Operational realism in the agent layer**: the relay replays `initialize` after a daemon restart (`mcp/src/relay.ts:97–118`), peers are redialed (`mcp/src/node.ts:300–345`), failures carry stable codes.
- **Engineering honesty**: every defect in KNOWN_ISSUES has a cause, a fix and a regression test. This is the project's main credibility asset.

### 2.2 Risks, ordered by severity

1. **Resource exhaustion in open-membership databases** (section 1.1 item 1). Identity blocks of unknown writers are fetched, verified and pinned before the access rule runs (`src/storage/helia.ts:223–227`), so even an allowlisted database has an unauthorized-identity surface (Codex). Head announcements are queued without deduplication or rate limit and each can wait out a fetch timeout (`src/sync.ts:31`, `src/database.ts:1106–1118`, `src/storage/helia.ts:155`).
2. **Writer-chosen timestamps order the tree.** A backdated entry forces a rebuild from its position to the end (`updateLayers`, `src/database.ts:946–971`); a far-future entry holds its key against normal writes. Under `namespace-per-writer` the second only hurts the writer; the first hurts every replica. Deterministic containment: a manifest-defined timestamp window in the validity rule, plus restricted membership. A local-clock check must stay out of the rules (specs/ordering.md §4 is right).
3. **In-memory index, rebuilt by re-verification on open** (`openDatabase` → `syncNewHead` → `load`, `src/database.ts:249–257`, `:1041–1093`). README numbers imply about one minute to reopen and 17–24 minutes for a fresh join at 100k records; an update to an old key rebuilds a long suffix (`src/database.ts:489`).
4. **Unbounded growth.** Superseded entries and old heads stay pinned, tombstones are permanent, nothing reclaims space (specs/succession.md is a draft).
5. **Key management.** One passphrase, supplied through the environment or a systemd env file, opens the device key and every agent key (`mcp/src/node.ts:287–295`). No rotation, no revocation. Encrypted values have no forward secrecy (`src/encryption.ts:109–124`); a lost data directory loses identity and decryption.
6. **Immutable membership.** An allowlist is a fixed list of machine keys; adding a laptop means a new database until delegation ships.
7. **No change feed.** `set`, `delete` and `processLeafMerging` know exactly which key changed and who wrote it, and emit nothing. Section 4 depends on this.
8. **One database per daemon** (`mcp/src/node.ts:391–412`). Real use between parties wants one database per collaboration. Codex correctly notes this is not a one-argument change: lifecycle, routing, persistence and aggregate limits all need design.
9. **Helia** (issue #29). Usage is narrow — blockstore/datastore, pins, dag-cbor, bitswap (`src/storage/helia.ts:19–177`) — so the exposure is contained. Replacing bitswap is still a real transport project: peer selection, framing, backpressure, retries, serving.
10. **Planned DHT discovery leaks the read secret.** Issue #31 keys provider records by the database address. Since "anyone who knows a database address and can reach a peer can replicate it" (ARCHITECTURE "Trust model"), announcing the address on a public DHT makes databases enumerable. Announce a derived key, for example a hash of the address with a fixed label, so that finding peers does not reveal what to ask them for.

### 2.3 Defects found in this review

| Where | Problem | Fix |
|---|---|---|
| `mcp/src/tools.ts:226–228`, `:285–287` | `memory_get` and `memory_list` call `db.get(key)` and then `db.provenance(key)`. A replacement landing in between yields an old value labeled with the new writer and time. Found by Codex; confirmed by reading the code. In a product whose point is attribution this matters | Read the winning record once and fetch the value by its entry CID ([#40](https://github.com/denkmitdb/denkmitdb/issues/40), KNOWN_ISSUES #35) |
| `mcp/src/relay.ts:105` | After a reconnect the relay sends `notifications/tools/list_changed`. Codex 0.166 has `mcp_tool_list_changed` under development and off, so Codex keeps stale schemas (the scenario of KNOWN_ISSUES #33) | Documented in docs/quickstart.md (Troubleshooting): restart the Codex session after a daemon upgrade |
| `src/database.ts:478–481`, `:511–514` | The access check runs before signing, but the validity check runs after `createEntry`/`createTombstone` has signed, stored and pinned the block. Every `VALIDITY_REJECTED` write leaves a pinned block | Evaluate validity on the would-be payload before storing, or unpin on rejection ([#41](https://github.com/denkmitdb/denkmitdb/issues/41), KNOWN_ISSUES #36) |
| `src/sync.ts:62–69`, `src/database.ts:937–942` | Background rebuild failures are logged and swallowed, and the pending marker is cleared before the rebuild runs; `waitUntilIdle()` returning does not prove the head was built (Codex) | Surface the last rebuild error to `memory_set`; retry |
| `mcp/src/tools.ts:279–295` | `memory_list` scans keys linearly, has no cursor or "since", and returns raw CIDs with no names | Covered by `memory_changes` and a profile convention (section 4) |

### 2.4 Simplify or cut

- **Embedded fallback under `DENKMIT_DAEMON=auto`.** A second, differently behaving deployment shape that quietly creates a private database when the daemon is down. Make `require` the default and embedded an explicit opt-in.
- **The `addrs.json` file rendezvous** (`mcp/src/node.ts:346–374`): only useful for several embedded nodes on one machine, which the daemon replaces.
- **`prefix-per-writer` for new databases**: a privileged creator contradicts the positioning. Keep evaluating it; stop offering it in the quick start.
- **Library onboarding**: the README example needs ten packages and twenty lines of libp2p wiring. Export the node factory that `mcp/src/node.ts` already contains.
- **No human or script interface.** There is no CLI besides the two servers. A `denkmit` command over the socket (status, get, list, send, inbox, watch) is about a hundred lines — the status probe used in this review was sixty — and it is the prerequisite for hooks, demos without an LLM in the loop, and secrets that never enter a model context.
- Keep the separate validity rule (Codex and I agree); it is where the timestamp window and value limits belong.

### 2.5 Scaling limits (judgment, not measurement)

| Dimension | Comfortable | Upper bound today | What breaks first |
|---|---|---|---|
| Records (live keys + tombstones) | 10k | about 100k | Reopen time, fresh-join time, suffix rebuilds |
| Peers per database | 5–10 | about 20 | Floodsub announcements every 30 s per peer, repeated compares |
| Concurrent writers | 1–3 | low single digits | Head churn and redundant merges |
| Value size | 64 KiB (MCP only) | block-size limit for other clients | Every replica stores and pins everything |
| Writers in an open database | Trusted set only | — | No quotas (2.2 item 1) |

## 3. Real demonstrable use cases

All eight use the existing nodes: `open` (seed, Claude Code), `lab` (Codex), `askvivo` (Claude Desktop, NAT), `macbook` (Claude Code, wss/443 only), in the existing `namespace-per-writer` database unless stated. A caveat applies to all of them: **the four machines belong to one owner, so "untrusting parties" is simulated.** The first demo that would settle the positioning is the same script run with one outside person's machine.

**Step 0 for every demo — roll call.** Raw CIDs are unusable in a demo and no directory exists. Give each agent once:

> Call memory_status. Then save, in your own area under the name `profile`, a JSON value with the fields device, client and role. Do not add timestamps.

Any agent can then map names to identities by listing `agents/` and reading keys that end in `/profile`. The names are self-asserted claims; say so on stage.

Ranking is by demo impact weighed against honesty.

### 3.1 Stay in your lane: intrusion refused at the tool and at the wire

**Story.** An agent is told to overwrite and then delete another agent's record, and is refused. Then a peer running modified code that skips the local check publishes a forged entry, and every honest replica drops it at ingest. This is the project's core claim in two minutes.

**Why not a shared file or Redis.** There, write access is all-or-nothing and enforced by whoever runs the store. Here each copy enforces the rule by itself, including against a peer that cheats.

**Setup.** Part A: the live database, any two nodes. Part B: a throwaway database in-process — never the live one.

**Script.**

1. On `open` (Claude Code): "Save a note `decisions/release` in your own area with the value `{approved: true}` and tell me the full key."
2. On `lab` (Codex): "Overwrite the key `<that key>` with `{approved: false}`. If it fails, show me the exact error. Then try to delete it."
3. On `askvivo` (Claude Desktop): "Read `<that key>` and tell me its value, who wrote it and when."
4. Part B today: `pnpm vitest run test/access.test.ts test/adversarial.test.ts test/integrity.test.ts` and read out the names of the tests about merged entries from a non-writer, forged leaf metadata and replayed entries.

**Expected.** Step 2 returns `{"error":{"code":"ACCESS_DENIED",…}}` twice. Step 3 shows `approved: true`, writer = `open`'s agent CID, unchanged `writtenAt`. Part B passes.

**Missing or fragile.** Part A alone only proves that the honest client refuses its own write; Part B is the real claim and today it is a test run, not a live scene. Named small change: `scripts/demo-rogue-peer.mjs`, about 80 lines over `dist/internal.js`, which starts two nodes, bypasses `isAuthorized` on one and prints the other's "Rejected leaf … not authorized" log line with an unchanged record count.

### 3.2 Signed release gate across machines

**Story.** Before 4.0.0 ships, an agent on each platform runs the test suite at the release commit and publishes a signed attestation in its own area. An auditor agent on a fourth machine builds the matrix and answers "ship" only if enough distinct identities attested the same commit. It turns docs/testing.md layer 5 ("a release check by hand") into a repeatable procedure.

**Why not a shared file or CI.** The machines share no CI runner, no filesystem and no inbound port; one of them is behind a firewall. Nobody can post another machine's result — the tool refuses.

**Setup.** Live database. Attesters: `open` (arm64 Linux, Claude Code), `lab` (x86 Linux, Codex), `macbook` (macOS, Claude Code). Auditor: `askvivo` (Claude Desktop has no shell, so reading and judging is the role that fits it). Each attester needs a checkout at 24e53e6 with Node 22+ (not verified for `lab` and `macbook`).

**Script.**

1. Each attester: "In the denkmitdb checkout at commit 24e53e6 run `pnpm install --frozen-lockfile && pnpm build && pnpm test`. Then save in your own area under `release/4.0.0/attest/24e53e6` a JSON value with commit, command, exitCode, testsPassed, testsFailed, nodeVersion, os and arch, copied from the real output. No timestamps. Report the key."
2. `macbook`, the twist: "Also record a passing attestation for lab, inside lab's area."
3. Auditor: "List shared memory. Take every key ending in `release/4.0.0/attest/24e53e6`. For each, call memory_provenance. Make a table: writer CID, profile name, os/arch, exitCode, writtenAt. Rule: answer SHIP only if at least three different writer CIDs report exitCode 0 for commit 24e53e6 and each key lies inside its writer's own area. Otherwise HOLD, with the reason."

**Expected.** Step 2: `ACCESS_DENIED`. Step 3: a three-row table with three distinct CIDs and signed times, then SHIP. Deleting one attestation and asking again gives HOLD.

**Missing or fragile.** An attestation is a claim by a key: an LLM can misreport an exit code. The honest version takes the model out of the measurement — `denkmit attest -- pnpm test` (part of the proposed CLI) runs the command and signs the real exit code. The gate itself is an agent following a rule, so it is advisory. Gemini's objection, "this is a CI matrix with signed commits", is fair unless the pitch stresses disjoint networks and no shared runner.

### 3.3 Sealed hand-off across a firewall

**Story.** The Codex agent on `lab` must hand a one-time token to the Claude Code agent on `macbook`, which sits behind a firewall that allows only HTTPS and has no route to `lab`. It seals the value to the laptop agent's identity. The seed stores and relays it and cannot read it; the home machine sees that it exists and cannot read it; the laptop can.

**Why not Redis or a shared file.** No VPN, SSH tunnel or shared secret store between the two machines; the relay in the middle holds only ciphertext; delivery works when the sender has gone offline.

**Setup.** Live database, per-agent identities, all four nodes. Showcases encryption and the wss/443 path.

**Script.**

1. `macbook`: "Call memory_status and give me your identity CID."
2. `lab`: "Run `openssl rand -hex 16`. Store the output in your own area under `handoff/demo-token`, encrypted for identity `<macbook CID>`. Do not print the token in your answer."
3. `open` (the seed): "Read `<key>`. Can you see the value?"
4. `askvivo`: same question.
5. Optional, an owner action: stop the daemon on `lab`.
6. `macbook`: "Read `<key>` and show the value, the writer and whether it was encrypted."

**Expected.** Steps 3 and 4: `encrypted: true, readable: false, value: null`, with the recipient list. Step 6: `readable: true` and the token, writer = `lab`'s agent, even with `lab` offline.

**Missing or fragile.** The token passes through two model contexts, so this is for pairing codes and low-grade configuration, not production secrets; `denkmit set --encrypt-for <cid> --stdin` and `denkmit get` would fix that. The recipient is a key held by the daemon, so any process of that OS user can read it. No forward secrecy. Key name, writer, recipients and size are public. Gemini calls it contrived ("age plus any channel"); the honest framing is the relay that cannot read and the absence of any point-to-point setup.

### 3.4 Two-key approval bound to content

**Story.** One agent proposes a risky change; a second agent from another vendor must approve it. The approval names the proposal's entry CID — a hash of the signed record — so editing the proposal afterwards silently voids the approval.

**Why not a shared file.** In a file anyone can write "approved by codex", and an approval is not tied to the bytes approved. Here the approver's key signs it, and the reference is a content hash.

**Setup.** Live database; `open` proposes, `lab` approves, `askvivo` is the gate.

**Script.**

1. `open`: "Save in your own area under `proposals/caddy-timeout` a JSON value describing this change: file, the exact diff, and the reason. Then call memory_provenance on it and report the entryCid."
2. `lab`: "Read the proposal at `<key>` and get its provenance. Review the diff. If you agree, save in your own area under `approvals/caddy-timeout` a value with `approves` set to the proposal's entryCid and a one-line reason."
3. `askvivo`: "Gate check: get the provenance of `<proposal key>`. Find every `approvals/caddy-timeout`. Answer APPLY only if an approval written by a different identity than the proposer names the proposal's current entryCid. Otherwise HOLD and say why."
4. `open`: "Change the diff in the proposal to raise the timeout to 300 seconds." Then repeat step 3.

**Expected.** First gate check: APPLY, naming two different writer CIDs. After the edit: HOLD — "the approval names bafy…A, the proposal is now bafy…B".

**Missing or fragile.** The gate is an LLM following instructions. A hard gate is a script or a PreToolUse hook: `denkmit verify-approval <key> --min 1`. The superseded proposal cannot be shown, because no tool reads history. Both agents belong to one owner.

### 3.5 Seed outage drill

**Story.** The claim under test is "no operator in the middle". Stop the seed: every node still reads its complete verified copy and keeps writing. Start it again: everything converges. The drill also shows, honestly, what is lost meanwhile.

**Why not Redis or Postgres.** Stop that server and every agent is blind. Here only the path between nodes is lost.

**Setup.** Live database; owner access to `open` to stop and start the daemon.

**Script.**

1. Owner: `systemctl --user stop denkmitd` on `open`.
2. `lab` and `macbook`: "Call memory_status: how many peers are connected? List everything in shared memory and count the entries. Then save a note `drill/<your device>` in your own area."
3. `macbook`: "Can you see a note `drill/lab` anywhere?"
4. Owner: start the daemon. Wait about a minute.
5. Any node: "List every key containing `drill/` with its writer."

**Expected.** Step 2: `connectedPeers: []` on `macbook`, a full listing, a successful write. Step 3: no. Step 5: both notes, each with its own writer.

**Missing or fragile.** Step 3 is the honest part: the two NAT/firewalled nodes have no path to each other without the seed. Named small change, configuration only: make `lab` a second seed (it has a public address), and give it a wss listener if `macbook` should use it. Circuit relays (issue #31) are the real fix.

### 3.6 No-delete decision ledger (validity rule)

**Story.** A team wants a decision log that nobody can retract. A second database carries a validity rule "puts only" next to the per-writer access rule; a delete is refused on every replica with `VALIDITY_REJECTED`.

**Why not a shared file or Redis.** The retention rule is part of the database's address and is enforced by every copy; no administrator can relax it afterwards.

**Setup — a named small change, configuration only.** A second daemon instance on two nodes (`open`, `lab`) with its own `DENKMIT_DATADIR`, `DENKMIT_SOCKET` and `DENKMIT_LISTEN` port, a second MCP entry (`denkmit-ledger`), and on first start `DENKMIT_POLICY_FILE` containing:

```json
{
  "access":   { "version": 1, "name": "ledger-access", "description": "own namespace only",
                "logic": { "startsWith": [ { "var": "entryKey" }, { "cat": [ "agents/", { "var": "entryCreator" }, "/" ] } ] } },
  "validity": { "version": 1, "name": "ledger-put-only", "description": "no tombstones",
                "logic": { "===": [ { "var": "entryOperation" }, "put" ] } }
}
```

Not run in this review; `smoke:daemon` already runs two daemons on one machine, so it should work.

**Script.** `open`: "In the ledger memory, record under `decisions/2026-11-10-release` in your own area: we ship 4.0.0 after the release gate." Then: "Delete that record." `lab`: "Read it and tell me who wrote it. Try to delete it yourself."

**Expected.** `open`'s delete: `VALIDITY_REJECTED`. `lab`'s delete: `ACCESS_DENIED` (access is checked first). The record stays.

**Missing or fragile.** This is no-delete, not append-only: the writer can still overwrite its own key with a later put, and rules cannot see whether a key exists. True immutability needs a value-digest input in the rules (roadmap, manifest v3). Each rejected delete currently leaves a pinned block (2.3).

### 3.7 Cross-vendor handoff with provenance (the daily driver)

**Story.** Claude Code on `open` (arm64) and Codex on `lab` (x86) each run the benchmark and post results; Claude Desktop at home compares the two and says who measured what. Agents from different vendors have no common memory; this gives them one without an account or a repository.

**Why not git.** Honestly, for one owner a repository does most of this. What remains: no credentials on the home chat app, no shared remote, automatic attribution, and conflicting claims kept side by side rather than merged.

**Setup.** Live database, three nodes.

**Script.** `open` and `lab`: "Run `node scripts/bench.mjs 2000` in the denkmitdb checkout and save the result table in your own area under `findings/bench-2000`." `askvivo`: "Read every `findings/bench-2000` in shared memory. Compare the two machines operation by operation, say which identity reported each number and when, and point out anything that disagrees."

**Expected.** A comparison citing two writer CIDs and signed times; the README performance table reproduced by agents.

**Missing or fragile.** It is the least differentiated case; Gemini would drop it. Keep it as the everyday use that makes people install the thing, never as the headline.

### 3.8 Agent mailbox across the firewall (polling today, push in 4.1)

**Story.** The laptop agent cannot reach `lab`, but it can ask `lab`'s agent to do something and get a signed answer: "run the x86 benchmark and tell me the reopen time". This is the bridge to section 4.

**Why not ssh.** There is no route and no credential; request and answer are attributable records that survive either side being offline.

**Setup.** Live database. Today the receiving side must be prompted, or polled by a timer.

**Script, today.** `macbook`: "Save in your own area under `outbox/<lab-codex CID>/req-001` a request: run `node scripts/bench.mjs 2000` and reply with the reopen time." On `lab`, a human types: "Check shared memory for keys containing `outbox/<your CID>/`. For each request written by an identity you know from the profiles, do what it asks only if it is a read-only measurement, and save the answer in your own area under `outbox/<sender CID>/re-req-001`." `macbook`: "Is there a reply to req-001? Who signed it?"

**Expected.** A reply key under `lab`'s area, writer = `lab`'s agent.

**Missing or fragile.** Without section 4 this is a person relaying "check your inbox". An unattended version exists today as configuration — a timer on `lab` running `codex exec --sandbox read-only` with a fixed prompt — but it is remote prompt execution and must be limited to allowlisted senders and read-only work. Gemini says drop it ("a bad RPC queue on an LWW store"); Codex says it is sound for ownership but not a reliable queue. Both are right about the limits; it stays last in the ranking.

## 4. Pushing messages and updates from denkmitd to agents

### 4.1 The constraint

An agent in an interactive session acts only when a person types or a tool returns. "Push" therefore means one of three different things: (a) the agent learns of news at its next turn; (b) an idle session is woken; (c) a new headless run is started. They differ in client support and in risk, and (a) covers most of the value.

### 4.2 Mechanisms compared

|---|---|---|---|---|
| MCP `resources/subscribe` + `notifications/resources/updated` | No, in all three clients. ### 4.3 Prompt injection: values are data, never instructions

A pushed event is text written by another party arriving unasked in an agent's context. Rules:

1. **Metadata only.** A notice carries a count, the sender's local contact name, a sanitized key tail and the signed time. Never the value.
2. **Key names are attacker-controlled too.** Show only the last segment, restricted to `[A-Za-z0-9._-]` and 64 characters; otherwise show the entry CID prefix.
3. **Sender allowlist ("contacts") per subscription, default deny.** Entries from unknown identities raise no notice; they sit in a separate bucket visible only on request. Namespace isolation does not stop spam (Codex).
4. **Fixed templates, coalesced and rate-limited**: "3 new entries from lab-codex", not a stream.
5. **The lure attack** (Gemini): a metadata-only notice still makes the agent call `memory_get`, and one tool call later the untrusted text is in context. Stripping values delays the exposure; it does not remove it. The real controls are the allowlist, the `byThisAgent: false` warning already in the tool description, and — for wakes — privilege separation: an inbox-processing run gets read-only tools plus `memory_send`.
6. **Never declare the channel permission-relay capability.** A database writer must not be able to approve tool calls.
7. **Wakes are opt-in per sender, with a fixed prompt, a read-only sandbox, a rate limit and an audit record** written back as a signed entry.

### 4.4 Recommended design

**Library — a change feed (the prerequisite).**

`db.subscribe(listener)` or `db.changes()` emitting `{ key, entryCid, writer, timestamp, deleted, origin }` with `origin` in `local | remote | restore`. Emit only when a record becomes the live winner (`result.applied`): after the index mutation in `set` (`src/database.ts:483–485`), `delete` (`:516–517`) and `processLeafMerging` (`:916–917`). `load()` replaces state (`:1068–1093`) and the restore on open goes through the same path (`:249–257`): emit one `reset` marker and tag those events `restore`, or every restart replays the database as news. Capture event data before the next `await`; isolate listener errors (Codex).

**Daemon — journal, subscriptions, inbox.**

- *Journal*: a bounded, durable log per database with a local sequence number and an epoch id. The promise is "you will learn the latest state of every changed key", not every intermediate transition. On start the daemon reconciles the index against a persisted `key → entryCid` map and synthesizes events for differences, which covers crashes and merges that happened without a consumer. A cursor from an old epoch gets an explicit "resync" answer.
- *Subscriptions*: per consumer (agent identity plus a client-chosen name, since several sessions share one identity — `mcp/src/daemon.ts:74`), with key prefixes, a writer allowlist and "exclude my own writes". Cursors and acknowledgements are local daemon state. The relay must re-establish subscriptions after a reconnect; today it replays only `initialize` (`mcp/src/relay.ts:156`).
- *Inbox convention*, compatible with `namespace-per-writer`: the sender writes in its own area, `agents/<sender>/outbox/<recipient>/<msg-id>`, with `<recipient>` an identity CID or `all`, and `<msg-id>` generated by the daemon (time-sortable plus random; never chosen by the model). Value: `{ v: 1, type: note|request|reply, subject, body, replyTo? }`, optionally encrypted to the recipient. The recipient's daemon indexes at ingest every key whose fourth segment is one of its identities and whose second segment equals the signed writer. This is not a prefix query — it needs its own index (Codex). Messages are immutable by convention: the daemon records the first entry CID seen per message key, reports a different one as "edited" and a tombstone as "retracted". Order is local arrival order; the signed time is shown as the sender's claim. Receipts are per message, `agents/<me>/receipts/<sender>/<msg-id>`, optional and off by default. No high-water marks (they skip late arrivals).

**Tools.**

- `memory_changes({ since?, prefix?, writers?, limit? })` → `{ events, next, epoch, reset? }`.
- `memory_inbox({ state?, limit? })` → metadata of messages for this identity; bodies through `memory_get`; `memory_ack({ keys })`.
- `memory_send({ to, subject, body, encrypt?, replyTo? })`.
- `memory_wait({ since, prefix? | inbox?, timeoutSeconds ≤ 50 })` — a long poll kept under Codex's default 60-second tool timeout.
- Every tool result gains one fixed line: `notices: { unread: n, cursor }`.
- A `denkmit` CLI over the same socket: `status`, `get`, `set`, `list`, `send`, `inbox`, `changes`, `watch`, `wait`, `contacts`.

**Phases.**

*Phase 1 — 4.1.0, "pull with a doorbell".* Change feed with reset semantics and restart tests; journal; `memory_changes`, `memory_inbox`, `memory_send`, `memory_ack`; the notice line; the CLI; contacts; documented hook recipes. No client-specific code in the daemon.

*Phase 2 — 4.2, "wake".* `memory_wait` and `denkmit wait`; the Claude Code `asyncRewake` loop; an opt-in channel adapter (the daemon declares `capabilities.experimental['claude/channel']` when `DENKMIT_CHANNEL=on`; the relay already forwards daemon-to-client lines unchanged); `denkmit watch --exec` for `codex queue … --resume`; OS notifications.

*Phase 3 — "unattended".* A wake runner driven by a local policy file (sender → fixed command template), read-only by default, rate-limited, audited; request/reply correlation; optional receipts.

*Not built:* resources as a delivery path, logging notifications, sampling, tool-description tricks, an exactly-once queue, a broker.

**Mapping to clients.**

| Client | Phase 1 | Phase 2 |
|---|---|---|
| Claude Code | `UserPromptSubmit` and `SessionStart` hooks (`mcp_tool` → `memory_inbox`, or `denkmit inbox --hook`); optionally a throttled `PostToolUse` for long autonomous runs | `asyncRewake` hook armed from `Stop`, or a background `denkmit wait`; channel adapter for always-on sessions such as the persistent `claude-main` tmux session on `open` |
| Codex | `hooks.json` with `SessionStart` and `UserPromptSubmit` running `denkmit inbox --hook`, trusted once through `/hooks` | `Stop` hook continuation; `codex queue --thread … --resume` from `denkmit watch --exec` |
| Claude Desktop | The notice line on every tool result, plus one sentence in the server instructions | Nothing more is available; OS notification to the person |
| No session open | `denkmit watch` | Wake runner (phase 3) |

## 5. Future development

### 5.1 Next 3 months — make the present claim solid

1. **Publish 4.0.0 / MCP 0.3.0.** Everything else is unobservable until `npm install` works.
2. **Fix the review findings in 4.0.x**: the attribution race, the validity-rejected pin, head-announcement deduplication and a per-peer rate limit, the Codex note on stale tools.
3. **One real second party.** Run 3.1–3.4 with one outside person's machine before the launch post. It changes "simulated" to "done" and will surface the onboarding problems (raw CIDs, immutable allowlists) with real force.
4. **4.1: push phase 1 and the `denkmit` CLI** (section 4).
5. **Persisted index snapshot** keyed by head CID, so reopen stops re-verifying every entry; **local GC** (succession layer A, no protocol change).
6. **DenkMit Logic 1 specification and test vectors** (#30). The language is already frozen into manifests; the spec is overdue rather than optional.
7. **A second seed and a documented multi-seed setup** — configuration only; it removes the single point of failure shown in 3.5.

### 5.2 Months 3–6 — one manifest v3

Bundle the format-changing work into a single version step, because each step costs a compatibility matrix and a migration story:

1. **Delegation phase 2, scoped down**: owner → device certificates, `entryOwner` as a rule input, `namespace-per-owner` and owner allowlists. No agent sub-chains and no revocation records yet; succession is the compromise remedy, as the spec already argues.
2. **Rule inputs for resource control**: value byte size, a value digest (which makes content-addressed, effectively immutable keys expressible — Gemini's suggestion, not expressible in Logic 1 today), and a static timestamp window. With these, "untrusting" starts to cover availability.
3. **Succession record** (specs/succession.md layer B), the only way to change rules or drop a compromised key.
4. **Push phase 2.**
5. **Sync protocol v2**: batched request/response over a libp2p stream for database blocks (#29), block store kept behind the existing narrow interface. It removes the 10 ms-per-entry wall and the dependency on bitswap; budget it as a real transport project.
6. **Reachability: circuit relay v2 and DCUtR first**, DHT discovery last and only with a derived rendezvous key (2.2 item 10).

### 5.3 Months 6–12 — prove "any replica can check"

1. **A second, independent verifier**: a small program in another language that takes a head and validates entries, rules and the tree against the spec. It is the most convincing evidence for the whole positioning and the real test of the Logic 1 spec.
2. **Multiple databases per daemon**, designed properly: per-database limits, routing, tool addressing.
3. **Key lifecycle**: an owner key kept offline, device re-issuance, passphrase from an OS keychain or a systemd credential rather than an environment variable.
4. **Iroh as a transport spike**, only after sync v2 has made the transport replaceable.
5. **CEL as policy language v2 only if a user's rule cannot be written in Logic 1 plus the new inputs.**
6. **An external security review** of the trust model once manifest v3 is stable.

### 5.4 What not to build

- Semantic or vector search, summarization, memory "intelligence".
- Rich merge types, transactions, compare-and-swap, leases, BFT agreement.
- An exactly-once message queue or a broker; the inbox stays a convention over signed records.
- "P2P git for agents" (ROADMAP "Future direction"): remove it. It is a second product and competes with Radicle.
- Revocation records with index recomputation, before succession exists.
- A public-DHT presence keyed by database address.
- Browser transports, dashboards, a hosted seed service, tokens or payments.
- A third deployment shape. Reduce to one: the daemon.

### 5.5 Decisions already made

No reason found to reopen DenkMit Logic 1 for 4.0.0, CEL as the v2 candidate, UCAN policy language for delegation restrictions, the rejections of json-rules-engine, Rego, Cedar and Biscuit, keeping libp2p, or Iroh as an option. Two points stated explicitly because they touch decided areas:

- **Discovery design, not the decision**: "DHT provider records keyed by the database address" (issue #31) should change to a derived key, and relays should come before the DHT.
- **Gemini argues against delegation** ("stick to static allowlists and raw keys"). I disagree and keep it on the roadmap in the reduced form above: with immutable manifests, static allowlists of machine keys make every membership change a new database, which defeats the cross-party use the project is positioned for.

## 6. Codex and Gemini: agreements and disagreements

**Codex (architecture).** Confirmed: in-memory index and linear reopen; the backdating rebuild as a practical denial of service; MCP-only size cap and absent quotas; no change feed; one database per daemon. Corrections I accepted: library writes and merges do not announce, only the MCP tools do, so there is no merge-announce feedback storm; "pinned forever" by a future timestamp is overstated, since a greater timestamp supersedes it; certificate expiry belongs to the draft delegation spec, not to current behavior; `memory_list` stops at the limit and is linear only in the worst case; the embedded fallback is logged and persistent rather than silent; multi-database support is not a small change; replacing bitswap is a substantial project that will not remove verification cost. Risks Codex added that I had missed: the unbounded head-announcement queue, identity fetch and pin before authorization, and the value/provenance attribution race. Its scaling judgment matches mine: 10k–100k records, 5–20 peers, low single-digit active writers. Remaining difference: Codex would keep the loose `==` operators because removing them changes existing policy semantics; I agree for Logic 1 and would only steer documentation and presets to the strict forms.

**Codex (push, and about itself).** Reported for 0.166.0: `mcp_tool_list_changed` off (verified with `codex features list`, which I reproduced); elicitation supported; hooks stable with context injection on SessionStart and UserPromptSubmit and continuation from Stop; `codex queue --thread … --resume` for injecting into an existing session (help text verified by me); MCP tool timeout 60 seconds by default. Marked by Codex as believed, not verified: no `resources/subscribe`, no model-visible logging or progress, no sampling. Design critique accepted: the outbox convention is sound for ownership but is not a reliable queue; the recipient needs an index because the pattern is not a prefix; per-message receipts instead of high-water marks; separate consumer ids; explicit reset and restore semantics; journal durability with epochs; the relay losing subscriptions on reconnect. Its build order equals my phase 1. It would defer wake, replicated acknowledgements and client-specific channels until delivery semantics hold; I agree on the order and keep the channel adapter in phase 2 as an opt-in.

**Gemini (positioning and use cases).** Agrees that the evidence is one owner and that availability is undefended. Harsher than me on two points, both partly adopted: a public VPS with a TLS proxy "is a server" — I changed the recommended claim to "no operator you have to trust"; and "stop using the word memory" — adopted for prose, not for tool names. Its ranking put the intrusion demo first and the content-bound approval second, which moved both up in mine; it called the release gate and the sealed hand-off contrived unless framed around disjoint networks and a relay that cannot read, and I took that framing. It would drop the cross-vendor handoff and the mailbox; I kept both at the bottom, labeled as the everyday use and the bridge to push. Use cases it proposed: a signed capability registry (folded into the roll call), a signed cache of expensive tool results (plausible; needs a writer allowlist against poisoning), and a "kill switch enforced by validity rules" — not expressible, since rules see one entry and cannot read other keys; I told it so and it did not contest.

**Gemini (push).** First answer: do not build push; polling a local replica is enough. After the objection that an interactive agent has nobody to trigger the poll: build turn-boundary hooks first, cut channels, move the wake runner later, and "do not pretend it is push — it is hook-driven polling". I agree with the naming and the order, and disagree with cutting channels outright: they are the only way to reach an idle Claude Code session, the adapter is small once the feed exists, and it stays behind a flag. Its most useful contribution is the lure attack (4.3 item 5). Its fix for messages on a last-writer-wins store — keys that must equal a hash of the content, checked by the validity rule — cannot be written in DenkMit Logic 1 (no hash operator, the value is not an input); it became the value-digest input in the manifest v3 list.

**Gemini (facts).** Used with caution. Corroborated elsewhere: Claude Code channels are a research preview requiring the development flag for custom servers (Claude Code docs); Codex hooks and `notify` (Codex docs and binary). Not corroborated: the exact contents of MCP revision 2026-07-28; Claude Desktop's client capabilities; the stewardship of Helia and js-libp2p after Shipyard; and three projects it named as positioning themselves on signed shared agent memory (Alethech, Constellate, emem). Those names should be checked before the launch post claims that nobody else does this.
